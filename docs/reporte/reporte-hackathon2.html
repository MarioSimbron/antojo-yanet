Resumen

Este reporte documenta cómo se llevó DulceBot, el asistente inteligente de la panadería Antojo de Yanet construido en el Hackathon 1, a WhatsApp, como proyecto del Hackathon 2 del Módulo 2, Automatización Inteligente con WhatsApp, del curso 1-META_IA-A de DEV.F. Ahora un cliente puede escribir desde su teléfono y recibir respuestas con datos reales del negocio: menú, horarios, políticas y encargos.

La solución cubre los cinco componentes que plantea el reto: una API de WhatsApp (Twilio WhatsApp Sandbox, porque no hubo acceso a la API de Meta), un webhook público con validación de firma, memoria por número de teléfono, function calling sobre la base de datos y seguridad en capas con Llama Prompt Guard 2. El canal nuevo reutiliza sin modificaciones el pipeline del Hackathon 1 y agrega lo que exige un canal real de mensajería: descartar mensajes duplicados, atender un mensaje a la vez por cliente, dividir respuestas largas y responder antes de que Twilio corte la conexión.

El canal está desplegado en Render y disponible las 24 horas. Se verificó con 23 pruebas unitarias (la suite de la API pasa 142 de 142), una prueba real desde WhatsApp que demostró RAG, memoria, herramientas y Prompt Guard (respuestas de 0.8 a 2.1 s en local) y una prueba en producción. Las pruebas en producción revelaron dos restricciones externas, el perfil KYC de Twilio y el límite de tokens por minuto de Groq, que se resolvieron con una respuesta síncrona por TwiML y un respaldo por la API REST.

Palabras clave: WhatsApp, webhook, Twilio, agente conversacional, memoria, function calling, Llama Prompt Guard.

1.Introducción

1.1 Contexto

En el Hackathon 1 se construyó DulceBot, un asistente que responde con datos reales de la panadería mediante RAG, function calling y prompt engineering dentro de la tienda web (Simbron Gonzalez, 2026). Ese reporte dejó WhatsApp fuera del alcance y lo listó como trabajo futuro. El Hackathon 2 pide que una persona converse con el sistema desde WhatsApp y que el modelo decida qué responder o qué acción realizar (DEV.F, 2026a).

1.2 Problema

Los clientes de una panadería de barrio preguntan por WhatsApp qué pan hay, a qué hora abren o cómo encargar un pastel, y alguien contesta cada mensaje a mano. Además, un canal de mensajería impone condiciones que el chat web no tenía: el mensaje llega a un servidor público, puede repetirse, el cliente escribe varios mensajes seguidos y el proveedor solo espera unos segundos.

1.3 Objetivo general

Que un cliente converse con DulceBot desde WhatsApp, con las mismas capacidades y defensas que en la tienda web, de forma segura y disponible para cualquier evaluador.

1.4 Objetivos específicos

  1. Recibir los mensajes de WhatsApp en un webhook público y verificar que provengan del proveedor.
  2. Mantener la memoria de la conversación por número de teléfono.
  3. Reutilizar sin cambios el pipeline del Hackathon 1 (Prompt Guard, RAG y herramientas).
  4. Garantizar el orden y evitar respuestas duplicadas cuando lleguen mensajes repetidos o seguidos.
  5. Responder dentro del tiempo que el proveedor permite, con un respaldo para las respuestas lentas.
  6. Desplegar el canal para que cualquier persona pueda probarlo sin ayuda del autor.

1.5 Metodología

Como en el Hackathon 1, el proyecto siguió desarrollo guiado por especificaciones. El autor escribió la especificación del canal (interfaces, algoritmo de normalización, deduplicación, bloqueo por número, comportamiento ante errores y criterios de aceptación), autorizó cada fase y cada desviación, y validó los resultados en su teléfono. La IA implementó y probó el código contra esa especificación, y nada se integró a la rama principal antes de funcionar de punta a punta.

1.6 Alcance

Cubre el canal para clientes (rol invitado), su despliegue y sus pruebas. No cubre un número propio aprobado por Meta, mensajes multimedia ni el carrito, que solo existe en la web.

2.Marco de referencia

La guía del Hackathon 2 organiza el reto en cinco componentes y una cadena esperada: el usuario escribe → el webhook recibe → se recupera la memoria → Llama decide → se ejecuta una función si hace falta → se valida la seguridad → la API envía la respuesta (DEV.F, 2026a). Este capítulo resume cada componente tal como se presentó en el módulo.

2.1 API de WhatsApp y webhook

La API de WhatsApp transporta los mensajes, pero no construye el agente ni decide qué responder: la lógica de negocio, la conexión con el modelo, la memoria, las herramientas y las validaciones siguen siendo responsabilidad del sistema propio (DEV.F, 2026a, 2026b). El webhook es el punto público por el que el proveedor entrega cada mensaje entrante; sin él no hay entrada al sistema. En el curso se usó la WhatsApp Cloud API de Meta con un túnel (ngrok o Cloudflare Tunnel) hacia el servidor (DEV.F, 2026b). En este proyecto el proveedor es el Twilio WhatsApp Sandbox, que cumple el mismo papel (Twilio, s. f.-a).

2.2 Memoria y estado de la conversación

El modelo no recuerda nada entre llamadas: la memoria pertenece al sistema que lo rodea (DEV.F, 2026a). En el Tema 6 la memoria se guarda por número de teléfono, y el criterio de éxito es responder bien a un mensaje que depende del contexto previo (DEV.F, 2026c).

2.3 Function calling

El modelo decide qué herramienta necesita, pero es el código externo el que ejecuta la acción real; después el modelo redacta la respuesta en lenguaje natural con el resultado (DEV.F, 2026a, 2026d). El Tema 7 propone además medir la latencia del ciclo completo (DEV.F, 2026d).

2.4 Seguridad

La guía distingue dos problemas: la seguridad del contenido (Llama Guard) y la protección de las instrucciones frente a la inyección de prompts (Prompt Guard) (DEV.F, 2026a; Meta, 2025). En un canal público aparece un tercer problema: cualquiera puede enviar peticiones al webhook, así que el servidor debe comprobar que vienen del proveedor. Twilio firma cada petición con el encabezado X-Twilio-Signature para ese fin (Twilio, s. f.-c).

4.Decisiones técnicas

Las decisiones se documentan en formato ADR: contexto, decisión y consecuencias (Nygard, 2011). Varias surgieron de las pruebas, no de la especificación original; esas se marcan como tales.

D1. Twilio en lugar de la WhatsApp Cloud API de Meta

Contexto
El curso usa la API de Meta, pero no hubo acceso a ella; el propio curso reconoció el problema y buscó alternativas.
Decisión
Usar el Twilio WhatsApp Sandbox, que ofrece un número compartido listo para pruebas y un webhook configurable.
Consecuencias
Mismo modelo de webhook que en el curso. La cuenta de prueba (trial) resultó no permitir mensajes entrantes (Twilio, s. f.-b), así que se agregaron 20 USD de saldo para desbloquear el sandbox (capítulo 5).

D2. Reutilizar el pipeline del Hackathon 1 sin modificarlo

Contexto
DulceBot ya tenía RAG, herramientas, memoria, Prompt Guard y filtro de salida, evaluados en el Hackathon 1.
Decisión
El webhook llama a procesarMensajeChat como cliente invitado. La especificación prohibió modificar el servicio, el RAG, la memoria y los guards.
Consecuencias
WhatsApp y la tienda comparten comportamiento y defensas. El canal se limita a lo propio de la mensajería.

D3. El número de teléfono es la sesión

Contexto
Twilio entrega los números móviles de México como whatsapp:+521…, con un «1» que el resto de los sistemas ya no usa.
Decisión
Normalizar el número (quitar el prefijo y convertir 521 + 10 dígitos en 52 + 10 dígitos) y usarlo como sessionId. La respuesta se envía al valor original de From, que es el que Twilio reconoce.
Consecuencias
La memoria funciona por cliente: «¿Y cuál me recomiendas de esos?» se respondió con los productos del mensaje anterior.

D4. Deduplicar y atender un mensaje a la vez por número

Contexto
El proveedor puede reenviar un mensaje, y un cliente puede escribir dos mensajes seguidos; procesarlos en paralelo mezclaría su historial.
Decisión
Un conjunto de MessageSid ya vistos descarta repetidos, y una cola de promesas por número procesa los mensajes en orden. Son unas 10 líneas, sin dependencias nuevas.
Consecuencias
Las pruebas fallan si se elimina cualquiera de los dos mecanismos. Ambos viven en memoria y se reinician con el servidor.

D5. Validar la firma de Twilio

Contexto
El webhook es público: cualquiera podría hacerse pasar por Twilio y consumir la cuota del modelo. La especificación no lo pedía.
Decisión
Validar X-Twilio-Signature y responder 403 si no coincide. La URL se reconstruye con los encabezados del proxy para que funcione detrás de ngrok y de Render. Una variable la desactiva solo para pruebas locales.
Consecuencias
En local y en producción, una petición sin firma recibe 403 y las de Twilio pasan.

D6. Responder con TwiML en lugar de la API REST (surgió de las pruebas)

Contexto
La especificación pedía responder 200 al instante y enviar la respuesta después por la API REST. Al actualizar la cuenta de Twilio, la API REST exigió un perfil KYC aprobado (error 20003). Un servidor de prueba aislado demostró que la respuesta en el mismo webhook sí se entregaba sin KYC.
Decisión
Esperar la respuesta de DulceBot y devolverla en el mismo webhook como TwiML <Message>, en partes de máximo 1600 caracteres (Twilio, s. f.-d).
Consecuencias
Las respuestas llegaron sin KYC. Se deja de cumplir el criterio «200 en menos de 500 ms» de la especificación: ahora el 200 tarda lo que tarda DulceBot.

D7. Límite de 12 segundos con respaldo REST (surgió de las pruebas)

Contexto
Twilio corta el webhook a los 15 s. En producción, las preguntas que usan herramientas tardaron entre 15 y 20 s por el límite de tokens por minuto de Groq.
Decisión
Si DulceBot no termina en 12 s, el webhook responde vacío y la respuesta se envía después por la API REST. El autor completó el perfil KYC para habilitar ese envío.
Consecuencias
Las respuestas rápidas llegan por TwiML y las lentas por REST; un envío REST de prueba quedó entregado sin errores. El cliente espera más en las respuestas lentas.

D8. Canal opcional

Contexto
La especificación pedía que el servidor fallara al arrancar si faltaban las variables de Twilio, pero así se caerían Render, Docker y las pruebas de quien no use WhatsApp.
Decisión
Seguir la convención del proyecto (como con Groq): sin las variables, el canal no se monta y se muestra un aviso claro.
Consecuencias
El resto de la aplicación funciona igual con o sin WhatsApp.

D9. Webhook en Render, mantenido despierto

Contexto
El revisor debe poder probar a cualquier hora, no solo cuando la laptop del autor está encendida. El plan gratuito de Render se duerme tras 15 minutos y tarda unos 40 a 50 s en despertar, más que los 15 s de Twilio.
Decisión
Apuntar el sandbox a Render y programar una consulta a /health cada 10 minutos con UptimeRobot.
Consecuencias
Servicio disponible sin costo adicional; depende de que el monitor siga activo.

D10. Botón «Abrir WhatsApp» en la tienda

Contexto
Para unirse al sandbox hay que enviar un código exacto a un número específico, un paso fácil de equivocar (capítulo 5).
Decisión
Agregar a la página de inicio un botón con un enlace wa.me que abre WhatsApp con join came-follow ya escrito. La especificación pedía no tocar el frontend; el autor decidió hacer esta excepción.
Consecuencias
Cualquier visitante puede probar el canal; también puede consumir saldo de Twilio, un riesgo limitado porque el saldo es prepagado y la recarga automática está desactivada.

6.Limitaciones y trabajo futuro

6.1 Limitaciones

  • Latencia variable: el plan gratuito de Groq permite 8,000 tokens por minuto (Groq, s. f.), y cada pregunta con herramienta hace dos llamadas al modelo; en producción algunas respuestas tardan hasta unos 20 s. Ningún otro modelo de la cuenta tenía un límite mayor, y el plan de pago no estaba disponible.
  • Sandbox compartido: solo responde a números que enviaron el código; la conexión dura 72 horas (Twilio, s. f.-a), y el código es público.
  • Memoria en RAM: el historial y los mensajes ya procesados se pierden si el servidor se reinicia.
  • Sin carrito en WhatsApp: DulceBot puede ofrecer «agregar al carrito», pero ese flujo solo existe en la tienda web.
  • Elección de herramienta: ante «¿hay stock de conchas?» el modelo eligió buscar_en_menu en lugar de consultar_stock, y respondió sin cantidades.
  • Solo texto: los mensajes con fotos o audios se ignoran.

6.2 Trabajo futuro

  • Registrar un número de WhatsApp propio de la panadería, para eliminar el código de unión y el límite de 72 horas.
  • Reducir los tokens por mensaje (menos contexto del RAG en producción) para no rebasar el límite por minuto, y medir el efecto en la latencia.
  • Guardar el historial por número en la base de datos.
  • Transcribir notas de voz con un modelo de voz a texto y procesarlas como texto.
  • Enviar al cliente un enlace al checkout prellenado en lugar de ofrecer el carrito.
  • Evaluar las conversaciones de WhatsApp con un juez automático, como en el Hackathon 1.

7.Conclusiones

DulceBot cumple el objetivo del Hackathon 2: un cliente puede conversar con él desde WhatsApp, y el sistema recorre la cadena completa que plantea el reto, de la entrada por el webhook a la respuesta por la API, pasando por la memoria, la decisión del modelo, las herramientas y la seguridad. El canal está desplegado y cualquier persona puede probarlo.

La primera lección es que separar el canal del agente dio resultado. Como el pipeline del Hackathon 1 no se tocó, el trabajo nuevo se concentró en lo que solo existe en un canal de mensajería: verificar quién envía, no repetir, no mezclar conversaciones y responder a tiempo.

La segunda lección es que en una integración real los problemas más difíciles están fuera del código. El tipo de cuenta del proveedor, la verificación de identidad, la versión de una herramienta, una URL olvidada y el límite de tokens de un plan gratuito detuvieron el sistema en distintos momentos; ninguno lo habría revelado una prueba unitaria. Como en el Hackathon 1, la regla fue diagnosticar con evidencia antes de corregir, y cada corrección quedó documentada.

Anexos

Anexo A. Cómo probarlo en WhatsApp

  1. Desde el celular, abrir wa.me/14155238886?text=join%20came-follow (o el botón «Abrir WhatsApp» al final de antojo-yanet.pages.dev) y enviar el mensaje que aparece escrito: join came-follow.
  2. Esperar la confirmación del Twilio Sandbox («You are all set!»).
  3. Escribir, por ejemplo: «¿Qué panes tienen?», «¿Y cuál me recomiendas?», «¿Abren los domingos?» o «Quiero un pastel de tres leches para el sábado».
  4. Si después de 72 horas deja de responder, volver a enviar join came-follow.

Anexo B. Cómo ejecutar el canal en local

  1. En Twilio: Messaging → Try it out → Send a WhatsApp message → Legacy WhatsApp Sandbox; unirse con el código propio de la cuenta.
  2. Agregar a api/.env TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN y TWILIO_WHATSAPP_FROM=whatsapp:+14155238886.
  3. Levantar la API (cd api && npm run dev) y exponerla con ngrok http 4000.
  4. En Sandbox settings, configurar https://<url-de-ngrok>/whatsapp/webhook con método POST.
  5. Pruebas del canal: npx vitest run tests/unit/whatsapp.test.ts (desde api/).
